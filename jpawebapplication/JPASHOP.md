# 엔티티 생성 시 주의 사항
  - 1:N 테이블일 경우 연관 관계의 주인은 N(FK가 있는 테이블)이 주인이다.
    - 1을 연관 관계의 주인으로 정하면 관리하지 않는 N테이블의 외래 키 값이 업데이트 되므로 관리와 유지보수가 어렵다.
    - 추가적으로 별도의 업데이트 쿼리가 발생하는 성능 문제도 있다.
  - 실무에서 @ManyToMany는 사용하지 말자 ! 
  - 실무에서 Getter는 열어두고 Setter는 꼭 필요할 경우에만 사용하자. 
  - 모든 연관관계는 지연로딩으로 설정 !
    - @XToOne 관계는 기본이 즉시로딩므로 직접 지연로딩으로 설정해야 한다.
    - 관련된 엔티티를 함께 DB에서 조회해야 하면, fetch join 또는 엔티티 그래프 기능을 사용한다.
  - 컬렉션은 필드에서 초기화 하자 !
    - 컬렉션은 필드에서 바로 초기화 하는 것이 안전하다.
    - null 문제에서 안전하다

# 제작하면서 배우는 점
  - service에서 조회 메서드에 @Transactional(readOnly = true) 를 사용하면 성능을 최적화 할 수 있다.
    - JPA가 조회하는 곳에서 성능을 최적화 한다.
    - 세션 플러시 모드를 MANUAL로 설정한다. 이렇게하면 강제로 플러시를 호출하지 않는 한 플러시가 일어나지 않는다.
    - 읽기 전용으로 영속성 컨텍스트는 변경 감지를 위한 스냅샷을 보관하지 않으므로 성능이 향상된다.
    - 참고 블로그 : https://willseungh0.tistory.com/75
  - 엔티티를 변경할 떄는 항상 변경 감지를 사용하세요.
    - 컨트롤러에서 어설프게 엔티티를 생성하지 마세요.
    - 트랜잭션이 있는 서비스 계층에 식별자(id)와 변경할 데이터를 명확하게 전달하세요.(파라미터 or dto)
    - 트랜잭션이 있는 서비스 계층에서 영속 상태의 엔티티를 조회하고, 엔티티의 데이터를 직접 변경하세요.
    - 트랜잭션 커밋 시점에 변경 감지가 실행됩니다.
    - 1:N 컬렉션 Fetch Join 할경우 페이징이 제한된다. 
    - 1:N 컬렉션 페이징을 하고 싶은 경우 ToOne 관계는 Fetch Join으로 가져오고, 컬렉션은 지연로딩으로 가져온다.
        - default_batch_fetch_size, @BatchSize 를 사용하여 데이터를 가져올 수 있다.

# 쿼리 방식 선택 권장 순서
    1. 우선 엔티티를 DTO로 변환하는 방법을 선택한다.
    2. 필요하면 페치 조인으로 성능을 최적화 한다. -> 대부분의 성능 이슈가 해결된다.
    3. 그래도 안되면 DTO로 직접 조회하는 방법을 사용한다.
    4. 최후의 방법은 JPA가 제공하는 네이티브 SQL이나 스프링 JDBC Template를 사용해서 SQL을 직접 사용한다.
